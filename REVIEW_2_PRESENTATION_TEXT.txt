SLIDE 4: ER-TO-NOSQL MAPPING & EMBEDDING STRATEGY
--------------------------------------------------------------------------------
The ER model is mapped to MongoDB using a hybrid Referencing and Embedding strategy:

RELATIONSHIP MAPPING:
• User -> Order: orders.userId (Referenced ObjectId)
• Restaurant -> Menu Item: menuItems.restaurantId (Referenced ObjectId)
• Category -> Menu Item: menuItems.categoryId (Referenced ObjectId)
• Restaurant -> Order: orders.restaurantId (Referenced ObjectId)
• User -> Review: reviews.userId (Referenced ObjectId)
• Restaurant -> Review: reviews.restaurantId (Referenced ObjectId)
• Order -> Order Items: Embedded inside orders.items[]

WHY EMBED ORDER ITEMS?
In a relational SQL database, order items require a separate normalized table (order_items) joined with orders. In MongoDB, embedding order items directly inside orders.items[]:
1. Allows retrieving the entire order and invoice in a single disk read ($O(1)$ lookup).
2. Avoids expensive multi-table joins.
3. Preserves historical pricing at the exact moment of order placement.

SLIDE 6: ADVANCED NOSQL FEATURE 1 - REVENUE AGGREGATION (CRITERION 3 - 5 MARKS)
--------------------------------------------------------------------------------
AGGREGATION PIPELINE 1: REVENUE AND ORDER VOLUME BY RESTAURANT
Purpose: Multi-stage pipeline calculating total sales revenue, order counts, and average order value per restaurant.

MongoDB Aggregation Pipeline Stages:
Order.aggregate([
  // Stage 1: Filter out cancelled orders
  { $match: { status: { $ne: 'Cancelled' } } },

  // Stage 2: Group by restaurantId and calculate metrics
  {
    $group: {
      _id: '$restaurantId',
      totalRevenue: { $sum: '$totalAmount' },
      orderCount: { $sum: 1 },
      avgOrderValue: { $avg: '$totalAmount' }
    }
  },

  // Stage 3: Join with restaurants collection
  {
    $lookup: {
      from: 'restaurants',
      localField: '_id',
      foreignField: '_id',
      as: 'restaurant'
    }
  },

  // Stage 4: Unwind the joined restaurant array
  { $unwind: '$restaurant' },

  // Stage 5: Project formatted fields
  {
    $project: {
      restaurantName: '$restaurant.name',
      cuisine: '$restaurant.cuisine',
      totalRevenue: 1,
      orderCount: 1,
      avgOrderValue: { $round: ['$avgOrderValue', 2] }
    }
  },

  // Stage 6: Sort descending by total revenue
  { $sort: { totalRevenue: -1 } }
]);

SLIDE 7: ADVANCED NOSQL FEATURE 2 - ARRAY UNWINDING ($unwind)
--------------------------------------------------------------------------------
AGGREGATION PIPELINE 2: TOP 5 BEST-SELLING DISHES
Purpose: Unwinds the embedded items[] array inside customer orders to aggregate individual dish popularity and revenue.

MongoDB Aggregation Pipeline Stages:
Order.aggregate([
  // Stage 1: Filter active orders
  { $match: { status: { $ne: 'Cancelled' } } },

  // Stage 2: Deconstruct embedded items array into separate documents
  { $unwind: '$items' },

  // Stage 3: Group by dish name and sum quantity and revenue
  {
    $group: {
      _id: '$items.name',
      totalQuantitySold: { $sum: '$items.quantity' },
      totalRevenue: { $sum: { $multiply: ['$items.price', '$items.quantity'] } }
    }
  },

  // Stage 4: Project clean field names
  {
    $project: {
      itemName: '$_id',
      totalQuantitySold: 1,
      totalRevenue: 1
    }
  },

  // Stage 5 & 6: Sort by quantity sold descending and limit to top 5
  { $sort: { totalQuantitySold: -1 } },
  { $limit: 5 }
]);

AGGREGATION PIPELINE 4: DYNAMIC RESTAURANT RATINGS FROM REVIEWS
Review.aggregate([
  { $group: { _id: '$restaurantId', averageRating: { $avg: '$rating' }, reviewCount: { $sum: 1 } } },
  { $lookup: { from: 'restaurants', localField: '_id', foreignField: '_id', as: 'restaurant' } },
  { $unwind: '$restaurant' },

SLIDE 9: ADVANCED NOSQL FEATURE 4 - DATABASE INDEXING STRATEGY
--------------------------------------------------------------------------------
Explicit indexes created to eliminate Collection Scans (COLLSCAN) and optimize query speeds:

1. restaurants Collection:
   - Index: { name: "text", cuisine: "text", location: "text" }
   - Type : Text Index
   - Optimization: Enables multi-field text search across restaurant names, food types, and locations with index scan (IXSCAN).

2. menuItems Collection:
   - Index: { restaurantId: 1, categoryId: 1, isAvailable: 1 }
   - Type : Compound Index
   - Optimization: Drastically accelerates menu filtering when customers select a restaurant and category.

3. orders Collection:
   - Index: { userId: 1, orderDate: -1 }
   - Type : Compound Index
   - Optimization: Allows instantaneous retrieval and reverse-chronological sorting of customer order histories.

4. reviews Collection:
   - Index: { restaurantId: 1, createdAt: -1 }
   - Type : Compound Index
   - Optimization: Accelerates review lookups and aggregation pipelines for calculating live ratings.

COMMON PROFESSOR VIVA QUESTIONS & ANSWERS:

Q1: Why choose MongoDB over Relational SQL for this project?
A1: Menus and orders are naturally hierarchical documents. Storing items inside orders.items[] eliminates multi-table joins, delivers faster read performance, and accurately captures order history. MongoDB also provides native aggregation pipelines for real-time analytics.

Q2: What is the purpose of the $unwind stage?
A2: $unwind deconstructs the embedded items[] array in each order into individual documents, allowing us to group by dish name and aggregate total quantities sold across all orders.

Q3: When do you use Referencing versus Embedding?
A3: We use Referencing (ObjectIds) for independent entities like Users, Restaurants, and Categories. We use Embedding for tightly coupled, 1-to-many child data like Order Items that are always accessed with the parent order.

Q4: What is the benefit of your compound index on menuItems?
A4: Without an index, MongoDB scans every document in the collection (COLLSCAN). The compound index { restaurantId: 1, categoryId: 1, isAvailable: 1 } enables an Index Scan (IXSCAN), reducing query complexity from O(N) to O(log N).
